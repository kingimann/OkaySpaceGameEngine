How to apply the blocks and privacy SQL (owner): Supabase dashboard > SQL Editor > New query > paste the whole of `docs/sql/blocks.sql` > Run. Apply it after `social.sql` (and after `follows.sql`, `profile_extras.sql`, `profile_showcase.sql` and `group_chats.sql` if you use them; it reads the `profiles` columns that exist when it runs). It is safe to re-run, and you should re-run it whenever a later SQL file adds a column to `profiles`. It takes effect immediately for players (no launcher restart; if the API still answers "could not find the table", wait a few seconds or run `notify pgrst, 'reload schema';`). **What changes for the API:** the presence columns (`last_seen`, `playing`, `session_code`) and the private profile columns (`bio`, `status`, `favorite_game`, `location`) can no longer be read straight from the `profiles` table by signed-in or anonymous API callers; they are read through the new `profiles_visible` view (same columns, hidden values are null). The launcher already does this and falls back to the table if the view does not exist. Anything else you built that reads those columns from `profiles` (a website, a script using the anon key) must switch to `profiles_visible`; the service role is not affected. Keep the helper schema `okay_private` out of Settings > API > Exposed schemas (it is not exposed by default). Check afterwards: Table Editor shows `blocks` and `privacy_settings` with RLS enabled; sign in as two test players, block one from a chat's menu, then try to message and friend-request from the blocked one (both are refused). To test it locally first: `OKAY_SQL_TEST_PGHOST=/var/run/postgresql bash tests/scripts/test_blocks_sql.sh` against a throwaway local Postgres (never a live project). Roll back (if you must): `drop view public.profiles_visible; grant select on public.profiles to anon, authenticated;` and drop the `okay_*` triggers and "okay rules" policies.
