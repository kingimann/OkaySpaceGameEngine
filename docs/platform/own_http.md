## Our own HTTP client (`okay::ownhttp`)

*Was `docs/own_http_client.md` until 2026-11-20.*

Status: **side by side, off by default, Linux only for HTTPS.** The spawned `curl` is still the default on every system except Windows (where WinHTTP is used) and is still the fallback whenever the own client cannot be used. Nothing has been removed. This is the curl row of `docs/status/own_code_roadmap.md`.

### The decision, in one paragraph

We write the HTTP/1.1 client ourselves. We do **not** write TLS. TLS is taken from the platform: WinHTTP on Windows (unchanged), the system OpenSSL (`libssl`) on Linux, loaded at run time with `dlopen` so that nothing is linked and a machine without it simply keeps using curl. macOS is not wired (see NOT DONE). Writing our own TLS is out of scope for the same reason as our own crypto (`docs/platform/crypto.md`): it needs an outside review we do not have, and a mistake there is a security hole.

### What it is

| File | What |
|---|---|
| `engine/include/okay/Platform/OwnHttp.hpp` | The pure layer: URL parser, request builder, response parser (status line, headers, Content-Length, chunked, close-delimited), redirects, limits. Talks to an abstract `Stream` and `Connector`; no sockets, no TLS, no OS headers |
| `engine/include/okay/Platform/OwnHttpNet.hpp` | POSIX transports: non-blocking TCP with deadlines, proxy settings from the environment, CONNECT tunnel, TLS through `libssl` loaded with `dlopen`, and `okay::ownhttp::Perform` that ties them together |
| `engine/include/okay/Platform/OwnHttpDownload.hpp` | Retries and downloads to a file, on top of `Perform`: `RetryPolicy` and `PerformWithRetry` (backoff with jitter, `Retry-After` in seconds or as an HTTP date, idempotent methods only), `DownloadToFile` (a temporary file unique to each run and locked while in use, SHA-256 while streaming with the engine's own `okay::crypto::Sha256`, expected hash and size, fsync, atomic rename, resume with `Range` and `If-Range` after a drop, progress, cancel). Written from RFC 9110 (sections 9.2.2, 10.2.3, 5.6.7, 13.1.5, 14, 15.3.7) and the POSIX `rename`/`fsync` manual pages; no client code consulted. No `<mutex>` or `<thread>` (waits use `nanosleep`) |
| `engine/include/okay/Platform/NativeHttp.hpp` | The callers' entry point (`okay::http::Request`, `NativeAvailable`). On POSIX it uses the own client only when built with `-DOKAY_OWN_HTTP=ON` **and** run with `OKAY_OWN_HTTP=1` |
| `engine/include/okay/Platform/OwnHttpInflate.hpp` | Thin wrapper (strict options) over the engine's ONE inflate, `engine/include/okay/Core/Inflate.hpp`, which is also used by PNG, the model readers and the FBX reader (there are no other copies any more). gzip and zlib decoder of our own (compression, not crypto), used only when a caller asks for gzip. Provenance: written from RFC 1950, 1951 and 1952 only, as a table-driven canonical Huffman decoder (first-level lookup on bit-reversed codes, slow path for codes over 10 bits, 64-bit bit buffer). No decoder source (zlib, puff, miniz, stb_image, libdeflate or any other) was consulted. An earlier version was flagged by an outside review as closely following a public reference decoder and was rewritten on 2026-11-14 (`docs/status/provenance_audit.md`); the rewrite has not itself had an outside review yet |
| `tests/test_inflate_differential.cpp` | The one inflate against a slow reference decoder written fresh from the RFCs (`tests/inflate_reference_slow.hpp`, one bit at a time): valid (Python zlib and hand-built), bit-flipped, truncated and spliced streams must give the same accept/refuse decision and the same bytes in lenient, PNG and strict mode; also checks the first-allocation clamp. `ctest -R inflate_differential` |
| `tests/test_own_http_inflate.cpp` | The inflate on its own: tables derived from the RFC rule, long Huffman codes, zip-bomb cap with measured peak heap, a differential run against Python zlib (2,400 streams), every prefix refused, fuzz |
| `tests/test_own_http.cpp` | Unit tests, hostile inputs and mutation fuzz of the pure layer (standalone, no engine) |
| `tests/test_own_http_net.cpp` | Integration tests against local servers, a local proxy and `openssl s_server` |
| `tests/test_own_http_download.cpp` | Retries and downloads against a local server written in the test (plain sockets): redirects 301/302/307/308 and a loop, chunked, gzip, drops, stalls and slow trickles with resume, a server that ignores `Range`, a file that changes between tries, a wrong `Content-Range`, 5xx and 429 then success with `Retry-After`, no retry for POST, wrong checksum, a 200 MB file with flat memory, a plain HTTP proxy and a CONNECT proxy to `openssl s_server`. Also the server and client for `scripts/own_http_bench.py` |
| `scripts/own_http_bench.py` | Our client against the curl program on the local server: wall time, CPU time and peak memory per process |
| `tests/scripts/gen_http_test_certs.sh` | Makes the throw-away test CAs and certificates (valid, wrong host name, expired, untrusted CA) |

All three headers are header-only. The only link-time addition is `libdl` (`${CMAKE_DL_LIBS}`), and only for builds that set `OKAY_OWN_HTTP`.

### Turning it on

- Build: `-DOKAY_OWN_HTTP=ON` (default `OFF`; ignored on Windows and macOS).
- Run time: environment variable `OKAY_OWN_HTTP=1`. Without it `okay::http::NativeAvailable()` is false and callers use curl exactly as before. `OKAY_HTTP_CURL=1` still forces curl.
- `OKAY_OWN_HTTP_LIBSSL=/path/to/libssl.so.3` replaces the library search list (no fallback to the default names when it is set).
- If the own client gets no HTTP response for any reason (libssl missing, certificate refused, proxy trouble, malformed answer, timeout), `okay::http::Result::reached` stays false, `Result::error` says why, and the existing callers run their curl path. Behaviour and signatures are otherwise those the callers already use: redirects followed, any HTTP status is `reached`, `outFile` streams to disk.

### HAVE / GAP

| Area | HAVE | GAP |
|---|---|---|
| HTTP/1.1 requests | Any token method, `Host`, `User-Agent`, `Accept-Encoding: identity`, `Connection: close` (or keep-alive when the caller asks: per-thread pool of 8; only GET, HEAD and OPTIONS ride on a kept connection, PUT and DELETE never do because a server may already have acted; one retry on a stale connection, only for those three methods and only when not one byte of the answer had arrived: a counter on the stream that Fill never resets, so a status line or header that began is never re-requested), `Content-Length` bodies, caller headers as `Name: value` lines | No shared pool across threads, no HTTP/2; no `Expect: 100-continue`; no request body streaming (body is a string or a file read into memory); no chunked request bodies |
| Response parsing | Status line, headers, `Content-Length`, chunked (extensions and trailers read and ignored), close-delimited bodies, HEAD/204/304, interim 1xx skipped | Trailers are discarded; no HTTP/2 or HTTP/3; no brotli or zstd; gzip and deflate only when the caller opts in (otherwise `Content-Encoding` other than identity is an error, and we ask for identity) |
| Strictness | Bare LF or CR in a head, obsolete line folding, NUL, duplicate or conflicting `Content-Length`, `Content-Length` with `Transfer-Encoding`, unknown transfer encodings, `101` upgrades, overflowing sizes: all refused | A close-delimited body (no length, no chunking) over plain HTTP cannot be told from a truncated one; over TLS OpenSSL 3 reports a missing close_notify as an error, and we treat that as a failure |
| Redirects | 301/302/303/307/308, absolute, relative, protocol-relative, dot segments, hop cap (10), https to http refused, 301/302/303 turn a non-GET into GET and drop the body, credentials (any header whose name has auth, key, token, secret, cookie, password or session in it) dropped when the origin changes | Cookies only through the opt-in per-call jar (host-only, simple); a cookie does not outlive the call; no `Refresh` header; no redirect policy callback |
| Injection | CR, LF, NUL and other controls in the URL, method, header names or values are refused before anything is sent; `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Accept-Encoding`, `Expect`, `Upgrade`, `TE`, `Trailer` cannot be set by callers; user info in a URL is refused | Callers must still percent-encode non-ASCII URLs (they are refused, not encoded) |
| Limits | Response head 64 KiB and 100 headers; body cap (64 MiB in memory, 8 GiB to a file by default in `NativeHttp`); connect timeout (8 s per address), silence timeout (30 s), total timeout (15 min, covers all redirects and proxy and TLS setup) | A hung resolver leaves a helper thread behind (the caller is released by `resolveMs`) |
| TLS (Linux) | `libssl` 1.1.0 or newer loaded with `dlopen` (`libssl.so.3`, `libssl.so.1.1`, `libssl.so`); TLS 1.2 or newer; SNI; chain verification (`SSL_VERIFY_PEER`); host name check with `SSL_set1_host` (no partial wildcards) or IP check with `X509_VERIFY_PARAM_set1_ip_asc`; verify result and peer certificate checked again after the handshake; refused (no connection made) when libssl cannot be loaded | No client certificates; no session resumption or ALPN; no OCSP, CRL or certificate pinning beyond what the system store and OpenSSL do; one `SSL_CTX` per CA setup is kept for the life of the process |
| CA store | `SSL_CERT_FILE`, `CURL_CA_BUNDLE` (files), `SSL_CERT_DIR`; else the system default store. A variable that is set but unusable is an error, never a silent fall back to something else | No Windows or macOS keychain integration in this client (Windows uses WinHTTP, which has its own) |
| Proxies | `HTTPS_PROXY` / `https_proxy` for https (CONNECT tunnel, TLS end to end with the origin), `http_proxy` / `HTTP_PROXY` for http (absolute-form request), `NO_PROXY` / `no_proxy` (suffixes, `*.` and leading dot, exact names and IPs, IPv4 CIDR, `*`); a proxy setting we cannot honour is an error, never a direct connection | `https://` proxies (TLS to the proxy), SOCKS, proxy credentials, `ALL_PROXY`, auto-configuration (PAC), IPv6 CIDR in `NO_PROXY` |
| Compression | Opt-in `acceptGzip` (`NetOptions`, `FetchRequest`): `Accept-Encoding: gzip, deflate`, `Content-Encoding` gzip, x-gzip and deflate (zlib) decoded by our own inflate; encoded body capped (64 MiB, held in memory), decoded body capped by `maxBodyBytes`, CRC-32 and size (gzip) or Adler-32 (zlib) must match, no trailing bytes, no stacked codings | brotli, zstd; no streaming decode (the encoded body is held whole); off by default and ignored for downloads to a file |
| Range and resume | `Range: bytes=N-` as a caller header; a 206 must have a valid `Content-Range` and a matching `Content-Length`; for `bytes=N-` and `bytes=N-M` it must start at N (and for N-M end at or before M); for `bytes=-N` the size must be known, the slice must end at the last byte and be at most N long; multipart/byteranges and answers to multi-range or malformed Range headers are refused, an unasked 206 is refused (`FetchResult::partial`, `rangeStart`, `rangeTotal`); `okay::http::RequestEx` resumes into a file (`resumeFrom`), restarts on a 200, leaves the file alone on 404 and 416 | Multiple ranges (any 206 or multipart/byteranges answer to a multi-range or malformed request is refused); suffix ranges (`bytes=-N`, passed through but not validated), `If-Range` is sent by `RequestEx` when `RequestOptions::ifRange` is set (the WinHTTP download path sets it from the first answer's strong ETag or Last-Modified) |
| Retries | `PerformWithRetry` and `DownloadToFile` (`RetryPolicy`): connect failures, timeouts, resets and connections closed early, and the answers 408, 429, 500, 502, 503, 504 are tried again, up to `maxAttempts`, with a doubling wait (`baseDelayMs`, capped at `maxDelayMs`) of which the share `jitter` is random; a `Retry-After` (seconds, or an HTTP date in any of the three forms) replaces the wait, and one longer than `maxRetryAfterMs` ends the retries. Only GET, HEAD, OPTIONS, TRACE, PUT and DELETE (idempotent, RFC 9110 9.2.2) are retried; POST and PATCH get one try. A cancel ends a wait. `OwnDownload` (`retries`) uses it | No retry budget shared across calls; PUT and DELETE are retried by `PerformWithRetry` (they are idempotent by the book) but no caller uses that yet; 501, 505 and other 5xx answers are final |
| Download to a file | `DownloadToFile`: the body goes to `<dest>.<key>.<pid>-<random>.part` (or `tempPath`), held under an exclusive `flock` while the run lasts, SHA-256 is computed while it streams, the size (`Content-Length`, `Content-Range` total, `expectedSize`) and the expected SHA-256 are checked, the file is fsynced and renamed over `dest` in one step, and the folder is fsynced; a wrong checksum, a size mismatch, a cap, a write error or a cancel removes the temporary file and leaves an existing `dest` untouched. After a dropped or stalled connection the next try sends `Range: bytes=N-` and `If-Range` (strong ETag, else Last-Modified); a 206 continues the hash, a 200 starts the file over, a 206 with another total or a 416 starts over, a 206 at the wrong offset is refused. `resumeExisting` takes over an unlocked temporary file left by an earlier run of the same download (same destination, same expected SHA-256; only with an expected SHA-256) and removes other unlocked leftovers of it; two downloads to one destination at once each get their own file. Memory stays flat (measured: 200 MB with no growth of resident memory) | Temporary files left by versions before this change (`<dest>.part`) are not taken over; a close-delimited body cannot be told from a cut one unless a size or hash is expected; no parallel ranges |
| Progress, cancel, timeouts | `FetchHooks::onProgress` (false stops), `NetOptions::cancel` (polled every 200 ms while connecting, resolving, waiting and reading), per-call `timeoutMs` on `okay::http::Request`, `RequestOptions` (`maxBytes`, `maxRedirects`, `connectMs`, `ioMs`, `totalMs`) | Windows keeps WinHTTP (WinHTTP keeps its session timeouts; `timeoutMs` is NOT applied on Windows, so Windows behaves as before) |
| Name resolution | `getaddrinfo` on a helper thread with `resolveMs` (8 s), the overall deadline and cancel; IP literals skip the lookup | A resolver that never answers leaves its helper thread behind until the process ends |
| Platforms | Linux and other POSIX with `dlopen`: pure layer, TCP, proxy, TLS. Windows: unchanged WinHTTP path. The pure layer and TCP/proxy code compile everywhere POSIX | macOS TLS (see NOT DONE) |

### Threat model

What this code verifies (and refuses to proceed without):

- The server's certificate chains to a CA in the configured trust store, is within its validity dates, and is valid for the host name (or IP address) in the URL, by OpenSSL's own checks. The same is checked again after the handshake. Nothing turns these off: there is no option, environment variable or retry that skips verification, and a failed verification never falls through to plain HTTP.
- TLS 1.2 or newer.
- Every byte we send in a header, URL or method is free of CR, LF, NUL and other control characters; callers cannot add headers that change message framing.
- Every byte we accept in a response head follows the strict rules above, sizes cannot overflow, and bodies and heads are capped, so a hostile server can cost at most the caps and the time limits.
- Credentials are not forwarded to a different origin on redirect, and a redirect from https to http is refused.
- A proxy only ever sees a CONNECT line (host and port) for https, never the request; the TLS session is end to end with the origin and verified against the origin's name.

What is trusted, and therefore outside what this code can guarantee:

- **The system CA store** (or the file or directory named by `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `SSL_CERT_DIR`). Whoever can write those, or the environment variables, can make us trust any CA. An environment that sets them (for example a corporate or sandbox proxy that re-signs TLS) is trusted by design.
- **The OpenSSL library found on the machine** (libssl and the libcrypto behind it): its TLS state machine, its X.509 parsing and verification, its random numbers. We load whatever the loader finds first among the default names; `OKAY_OWN_HTTP_LIBSSL` and the library search path decide which one. A vulnerable or replaced library is a vulnerable client. We do not pin versions beyond requiring 1.1.0 or newer.
- **The proxy**, for availability and for seeing which host is being contacted (not content).
- The operating system's sockets, name resolution and clock (certificate dates).
- Our own parser is new, unreviewed code. It has unit tests, hostile-input tests and fuzzing under sanitizers, but no outside review. This is the reason the own client is off by default.

### NOT DONE

- **macOS:** no TLS. `OwnHttpNet.hpp` compiles there (TCP, proxy), but `TlsApi::DefaultNames()` is empty and `NativeHttp` does not enable the client on Apple systems, so macOS keeps spawning curl. A real answer needs Network.framework or Secure Transport (Objective-C or C APIs), which could not be tested here.
- **Windows** is unchanged (WinHTTP); the own client is not used there.
- HTTP/2 and HTTP/3, a pool shared between threads, request body streaming, `Expect: 100-continue`.
- brotli and zstd response bodies; streaming gzip (the encoded body is held in memory).
- A persistent or shared cookie jar, full RFC 6265 rules (Domain, Expires, SameSite), authentication schemes (Basic, Digest, Negotiate), `Authorization` is only passed through as a caller header.
- Proxy credentials, `https://` and SOCKS proxies, PAC files, `ALL_PROXY`.
- Client certificates, certificate pinning, OCSP stapling checks, ALPN, session resumption, TLS 1.3 early data (not used).
- A hung resolver is bounded by `resolveMs`, but only the "name does not exist" and "cancelled" cases are tested; a resolver that never answers is not simulated.
- The connect timeout (`connectMs`) is not tested against a black-holed address (it needs a non-local network); the silence and total limits are.
- Memory with gzip on: the encoded body is held in memory (capped) and then the decoded body is built, so the peak is about THREE times the cap (the encoded body, the decoder's working buffer and the string copy of the decoded body; each is at most `maxBodyBytes`, 64 MiB by default, so up to about 192 MiB). Without gzip a body in memory is held once.
- Timeouts and re-sending: on Windows the per-call `timeoutMs` is not applied (WinHTTP keeps its session timeouts, as before this work). With the own client, a request that was written to an open connection and then failed (timeout, reset, bad answer) sets `Result::maybeSent`; `AccountService::HttpRequest` then does NOT send a POST, PUT, PATCH or DELETE again through curl (a GET or HEAD may be repeated). A clean not-reached (DNS failure, connection refused, TLS refused, bad URL) still falls back to curl. A body cut short by a timeout or an early close fails the whole call on the own client (`reached` stays false). On Windows (WinHTTP), `maybeSent` is set for ANY failure after `WinHttpSendRequest` succeeded (timeout, reset, invalid reply, a failed `WinHttpQueryDataAvailable` or `WinHttpReadData`), and a read error or fewer bytes than `Content-Length` also makes the call fail (`reached` false, no partial body). The decision is `okay::http::ShouldFallBackToCurl(method, result)` (tested for every method). Compiled with the MinGW syntax check only: unverified at run time (no Windows machine).
- Memory: the response head and chunk lines are capped, but a body into memory is held whole up to the cap (64 MiB); a download to disk streams, with the cap at 8 GiB. The Windows and curl paths have their own limits; the Windows body loop was not touched.
- The `own-http` CI job ran and passed on GitHub for PR #850 head `1b455cfa` (including its ASan and UBSan step) and has been green on main since #852. Still unverified: real servers, Windows and macOS. No run with OpenSSL 1.1.x; no clang or MSVC build of the tests; no sanitizer run of the engine-linked `NativeHttp` path (the net test includes `NativeHttp.hpp` standalone).
- Retries and resume are used by `OwnDownload` (launcher game downloads, official game files, the launcher's `Download()`, the Versions page, the editor update download, each with `retries = 2`); the account calls (`AccountService::HttpRequest`) and PlayFab do not retry (they are POSTs or need their own decision). No caller passes an expected SHA-256 yet: the Versions page still checks the hash from `versions.json` after the download, as before.
- Replacing the other curl uses: since #852 (merged) every runtime curl use on Linux tries the own client first (opt-in): `launcher/VersionsNet.cpp` `DownloadFile`, the launcher's cancellable game and official-game downloads, size probes and link preview, the editor's update download and PlayFab; curl is the fallback in all of them. The `main.cpp` blocks are compiled but have not been run on a desktop. `scripts/*.sh` are build tooling and stay. Full list and plan: `docs/platform/own_http.md`.
- Windows certificate store and Windows at all: Windows keeps WinHTTP. A readiness table and the flip criteria are in `docs/platform/own_http.md`.
- Making it the default, and dropping curl from the docs and the install notes. That needs the outside review above and a period of the opt-in being used without fallbacks.
- Tested only against OpenSSL 3.0.13 on Linux. OpenSSL 1.1.x is supported in the code (symbol names, minimum version through `SSL_CTX_ctrl`) but was not run.

## Own HTTP client: readiness for replacing curl

*Was `docs/own_http_readiness.md` until 2026-11-20.*

This page answers one question: what must `okay::ownhttp` do before the default can flip from curl to our own client, what does it do today, and what is left. The client itself is described in `docs/platform/own_http.md`; the removal rules are in `docs/status/own_code_roadmap.md`. Nothing here flips anything: `OKAY_OWN_HTTP` is still OFF by default, every curl path is still in the code (the own client always goes first and curl is the fallback), and Windows still uses WinHTTP. Every call site below that says "own client first" only does so when the program was built with `-DOKAY_OWN_HTTP=ON` and is run with `OKAY_OWN_HTTP=1`.

Status words: **Done** (code and a test that runs), **Partial** (works for the callers we have, with a stated limit), **Missing** (not written). "Proof" is the file that shows it.

### 3. What changed for readiness: which PR added what

- **PR #850 (merged; its title wrongly says "keep-alive, HEAD, conditional requests, cookies"; the title cannot be changed on the merged commit):** gzip and deflate (own inflate), Range and resume, progress, cancel, the name-lookup timeout, `RequestEx`, the per-call timeout on the own client, the launcher `DownloadFile` move, the `own-http` CI job. It does NOT contain keep-alive, HEAD requests as a feature, conditional requests or cookies.
- **PR #852 (merged as `bb5a977e` on 2026-11-14):** keep-alive (GET, HEAD, OPTIONS only), HEAD requests, conditional requests, per-call cookies and moving the launcher, editor and PlayFab call sites onto the client. (This page used to say "open draft, not merged"; it is merged, and everything below describes main with it.)
- **Review fixes (merged as #853):** Windows timeouts back to what they were, no curl re-send of a POST that may have been sent, strict Range checks, loopback tests for the redirect cap, and the CI and memory notes. **Review fixes of #852 (merged with it):** PlayFab no longer re-sends a POST through curl; the keep-alive retry counts bytes received; PUT and DELETE are off the pool; `requestSent` is set before every write; tests that could not fail were fixed.

Details of #850:

- `OwnHttpInflate.hpp`: the thin string wrapper over the engine's ONE inflate (`engine/include/okay/Core/Inflate.hpp`, since the merge of the three copies; see `docs/content/model_readers.md` and `docs/status/provenance_audit.md` row 11). gzip and zlib decoder of our own (compression, not cryptography), wired behind `acceptGzip` and `Limits::allowGzip`; off unless asked for, so every existing test and caller behaves as before.
- Range handling in `Fetch`: strict `Content-Range` checks, `FetchResult::partial/rangeStart/rangeTotal`.
- `FetchHooks::onProgress`, `NetOptions::cancel`, `NetOptions::resolveMs`, a resolver on a helper thread.
- `okay::http::RequestEx` (progress, cancel, resume, size cap, timeouts, gzip) and a `timeoutMs` argument on `okay::http::Request`; the account layer passes its per-call timeout to it (before, only the curl fallback honoured it, so with the own client on, the join-time ticket call could wait up to 15 minutes). On Windows (WinHTTP) it is applied too (claude/third-party-1, PR #1186 review): `Request` runs on `WinRequestEx`, whose small watcher thread ends a call that is blocked on a silent server when the time is up or the caller cancels (WinHttpCloseHandle on the request). Unverified until the Windows test job runs `winhttp_loopback`. A timeout on the own client no longer leads to a second send of a POST by curl (`Result::maybeSent`).
- `launcher/VersionsNet.cpp` `DownloadFile` tries the own client first (only when built with `OKAY_OWN_HTTP=ON` and run with `OKAY_OWN_HTTP=1`), then curl. The Windows timeouts are untouched (the review fixes removed a per-request WinHTTP timeout that #850 had added). Windows changes made by request (not run on Windows; syntax-checked with MinGW only): any WinHTTP failure after the send succeeded marks the call as maybe-sent (so a POST is not re-sent through curl), and a failed body read or a body shorter than `Content-Length` now fails the call instead of returning a cut body with status 200. The decision is `okay::http::ShouldFallBackToCurl` (tested for every method, and end to end through `AccountService` with a counting server and a fake `curl` on PATH).
- **Rule for PR #852 (pooled connections), done in #852:** `FetchResult::requestSent` is set immediately before EVERY write of request bytes: the fresh, the reused and the retried path all pass the one write in the attempt loop, and the flag is set right before it (test: a reused connection that fails after the write leaves `requestSent` true).
- Tests: after #850 `test_own_http` had 3,961 checks (was 147), `test_own_http_net` 181 (was 156), `test_launcher_download_own` 6 (new); the CI `own-http` job builds and runs the third. After the review fixes (20,000 fuzz iterations, ASan and UBSan, run here): 3,987, 193 and 7.

#### The fourth change: a faster SHA-256 and a unique temporary file (branch `claude2/own-http-sha-fast`)

- **SHA-256 speed.** `okay::crypto::Sha256` (shared engine code, header-only) got faster with byte-identical output: a fully written-out portable block function with the message schedule computed on the fly, and the x86 SHA extensions when the CPU has them (picked once at run time; `OKAY_SHA256_PORTABLE=1` forces the portable one). 1 GiB in 64 KB pieces on this shared machine (load average 6 to 10, so absolute numbers move a lot): before 137 to 169 MB/s; portable now 154 to 169 MB/s under that load, and about 9 % faster than before in a quieter repeated 4 MB test (300 to 305 against 330 MB/s); with the SHA extensions 700 to 1,250 MB/s (about 1,500 MB/s in the 4 MB test). Nothing changed about which crypto library is used for anything (CLAUDE.md rule 18): SHA-256 was always our own code.
- **The comparison again** (`scripts/own_http_bench.py`, 200 MB, same machine, load average 8.5 to 12.8; "curl + SHA-256 after" uses the same, now faster, own hash for its second pass):

  | The same after this change (three runs of 5, 9 and 9) | 0.77 / 0.94 / 1.01 s wall, 0.30 to 0.31 s CPU, 4.2 to 4.5 MB | 0.72 / 0.91 / 0.96 s, 0.31 s, 10.7 MB | **Met in all three** (wall 104 to 106 %, CPU 99 %, 6.2 to 6.6 MB less memory) |

  The whole download with its check is now about 2.5 times quicker in wall time (2.0 s to 0.8 to 1.0 s for 200 MB) and CPU time fell from 0.9 s to 0.3 s.
- **Temporary file.** Two downloads to the same destination used to share `<dest>.part`. Each run now writes `<dest>.<key>.<pid>-<random>.part` (key: the first 16 hex digits of the expected SHA-256, or `nosha`) and holds an exclusive `flock` on it. `resumeExisting` takes over an unlocked file of the same download (left by a run that ended), and clears away other unlocked leftovers of it. Tests: two downloads to one destination at once, a leftover taken over by exactly one of two runs started together, a file in use never taken over, a caller-given `tempPath` in use refused, stale leftovers cleared (`test_own_http_download.cpp`, 98 checks).

### 5. How close the flip is (honest estimate)

Call sites on Linux: 9 of the 9 runtime places that used curl or HTTP now try the own client first; the five download places (rows 3, 5, 7, 8, 9) now go through `DownloadToFile` (temporary file, SHA-256, resume, retries). Client features the callers need: all present except proxy credentials, SOCKS and HTTP/2 (not needed for correctness), and a Windows certificate store (a decision, not code). Flip criteria met: 0 of 6 fully; 2 partly (fuzz; speed and parity with curl); criterion 4 has no known bugs but known gaps.

For Linux builds the code is about 85 percent of the way. What is missing is not code but evidence: a CI run on GitHub, real servers, a soak run, an outside look at the parser, and owner approval. Putting a number on the whole flip: about 40 percent, because four of the five criteria are evidence criteria and none of them has been started beyond local tests. It is not ready to flip and nothing should be flipped on this page's word.

For the whole product it is much further away: Windows is 0 percent for the own client (it needs a TLS answer first), and macOS is not started. Removing curl as a dependency also needs the call sites to stop falling back to it (one release after a flip, as `docs/status/own_code_roadmap.md` says), and Windows still uses PowerShell or curl as the fallback in the launcher and editor downloads.
