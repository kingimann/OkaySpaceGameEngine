# okay-cc

Internal note. Not a user guide. It stays off by default: not in the engine CMake, not in CI, and not in releases. The engine does not include it. Built only by `tools/okaycc/build.sh`. This is our own compiler, not a replacement for MSVC or Clang.

Every line is written here from the documents named below. No copied compiler source, no third-party libraries, no cryptography.

## Status

- The lexer, preprocessor, parser, and type checker work for a C subset (`void`/`char`/`short`/`int`/`long`, signed and unsigned, `typedef`, casts, pointers, arrays, structs, `sizeof` of a type or an expression, functions, control flow, `switch` with `case`, `default`, `break`, and fallthrough, function pointers and arrays of them, `enum`, `union`, and global initializers for arrays, structs, and strings). Diagnostics use the source file name and the line number.
- The intermediate form is three-address code. Integers, calls, control flow, pointers, arrays, globals, string literals, and structs are lowered. Object sizes follow the System V AMD64 data model: `char` 1, `short` 2, `int` 4, `long` and pointers 8. Struct fields are aligned to those sizes. A struct of 1 to 8 bytes is passed and returned in one register, 9 to 16 bytes in two registers, and a larger struct in memory. The caller passes a hidden pointer for a large return. Multi-dimensional arrays use the element size as the step. A pointer to the struct being defined carries that struct's fields.
- The x86-64 code generator emits System V assembly for that subset. Tests assemble it with the system assembler and link it with the system linker (`gcc`). Narrow integers are sign-extended when loaded. An `int *` steps by 4. A `char *` steps by 1.
- A call to `write` is the Linux write system call, so a program can print without a C library. The same programs are compiled with the system gcc and the exit code and standard output are compared.
- The whole test suite has been run with AddressSanitizer and UndefinedBehaviorSanitizer on the compiler (`SAN=1 tools/okaycc/build.sh`). That run was clean.
- `long double` is accepted as `double`. A C++ subset has started. It accepts `namespace`, references, `bool` (one byte; a conversion or a store becomes 0 or 1), `nullptr`, `new` and `delete` as calls to `malloc` and `free`, and a non-virtual member function defined inside a `struct`. A namespaced name and a member function are mangled in the Itanium way for this subset (`_ZN1N1xE`, `_ZN1S3getEv`). `class`, virtual functions, templates, and exceptions are not accepted. okay-cc cannot compile its own lexer yet: that file includes C++ headers (`string`, `vector`, `cstdint`, and the rest of the standard library) which this compiler does not provide. `#pragma once` skips a file that was already included; any other `#pragma` is a warning and the line is ignored. `float` and `double` use SSE2 (`movsd`/`addsd` and the float forms). Arguments go in `xmm0`–`xmm7` and a result comes back in `xmm0`, per the System V ABI. The optimizer is a separate pass: it folds constants, propagates constants and copies across blocks, and deletes dead code. A linear scan keeps integer values in `rbx`, `r12`–`r15`, `rsi`, `rdi`, and `r8`–`r11`. A caller-saved register that is still needed after a call is stored to its stack slot and loaded back afterwards. Address-taken values stay on the stack. The ELF writer encodes x86-64 instructions itself. It writes a static executable and a relocatable object with a symbol table and `R_X86_64_PC32`, `R_X86_64_PLT32`, and `R_X86_64_64` relocations. `okay-ld` links those objects into one executable. A small libc (`write`, `exit`, `memcpy`, `memset`, `strlen`, `strcmp`, `strcpy`, `strcat`, `atoi`, `puts`, `printf`, and a coalescing free-list `malloc`/`free`/`realloc`/`calloc` on `brk`) is C compiled by okay-cc; `syscall` is the Linux syscall instruction. `printf` accepts a width, left adjustment, zero padding, `%ld`, `%u`, and `%f`. A variadic function saves the six integer argument registers and the caller sets `al` to 0. `include/stdarg.h` is for okay-cc; gcc keeps its own. Those paths do not use the system assembler or the system linker. The assembly path still does. A COFF writer emits an x86-64 relocatable object (file header, one or more sections, relocations, and a symbol table) from the PE/COFF specification. It is not connected to the code generator yet, and it shares no code with okayms. The driver is `okay-cc`.
- C++ classes (round 10, step 1). `class` and `struct` accept access labels (read, not enforced), constructors with member initializer lists, destructors, overloaded constructors (the checker picks by argument count, then by how well the types fit), single inheritance (the base fields are copied to the front of the derived class, so a base pointer is the same address), member functions defined outside the class, `this`, `extern "C"`, and a class name used as a plain type name. A local object runs its constructor at the declaration and its destructor at the end of the block, before `return`, `break` and `continue`, in reverse order. A class member and a base class run their own constructors and destructors (an implicit constructor or destructor is made when one is needed). `new T(args)` allocates and runs the constructor; `delete p` runs the destructor, then frees. Names follow Itanium C++ ABI 5.1: `_ZN3FooC1Ei`, `_ZN3FooD1Ev`. Data layout follows the Itanium ABI rule that a base which is "POD for layout" keeps its tail padding. Not done: copy and move constructors (an object is copied bytewise), `operator=`, global objects with constructors, arrays of class objects, access checking, multiple and virtual inheritance, exceptions, `goto` out of a scope that has objects with destructors. The new test group is `tests/progs_cpp/*.cpp`, run by `tests/test_cppdiff.cpp`: each program is compiled by okay-cc and by `g++ -std=c++17` and the exit code and output must match.
- C++ virtual functions (round 10, step 2). A class with a virtual function has a vtable pointer at offset 0 (`__vptr`). The vtable symbol is `_ZTV<class>`; it holds offset-to-top (0), the type-info pointer (always 0: there is no RTTI), then the function slots in declaration order, where a function that overrides a base function (with or without the word `virtual`) takes the base slot, and a virtual destructor takes two slots (complete-object `D1`, then deleting `D0`). A virtual call is the sequence `(*(void***)obj)[slot]` called with `obj` as the first argument. Each constructor stores its own class's vtable address after the base constructor ran, and each destructor stores it before its body, so a virtual call inside a constructor or destructor reaches that class's own function. `= 0` leaves a null slot (no `__cxa_pure_virtual`). The tests read the object's vtable by hand (offset-to-top, a slot called as a plain function) and compare with g++. Not done: a polymorphic class whose base is not polymorphic (the vtable pointer would shift the base), multiple and virtual inheritance, RTTI (`typeid`, `dynamic_cast`), covariant return types, `override` and `final` are read and ignored, a virtual call on an object expression with side effects is refused, and the `D2` base-object destructor.

## Written from

- ISO/IEC 9899 (C) and ISO/IEC 14882 (C++) for the language.
- System V AMD64 ABI for the calling convention the code generator will use. The Windows x64 convention is later.
- Intel 64 manual for instruction encodings.
- ELF and COFF specifications for object files, when those writers are built.
- Round 10 C++ classes: the class, constructor, destructor and member-initializer rules of ISO/IEC 14882, and the Itanium C++ ABI (data layout, name mangling, vtable layout, virtual call sequence). Nothing was copied from another compiler.

A full C++ compiler is still a very large piece of work. Nothing here is "ready" to replace another compiler.
