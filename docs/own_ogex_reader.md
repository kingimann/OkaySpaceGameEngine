# Our own OpenGEX reader (`.ogex`)

Status: **side by side, off by default** (`OKAY_OWN_OPENGEX`, same rules as `docs/own_3mf_reader.md`). Assimp (when built) is still the only other reader of OpenGEX files. Nothing was flipped. **Unverified against real files:** there is no `.ogex` file in this repository (nor under `assets/` or `tests/`), so every test below uses a file written by hand for this purpose.

## How to try it

Full steps: `docs/try_it.md`, section 8. Short form: start the editor from a Command Prompt with `set OKAY_OWN_OPENGEX=1` (or build with `-DOKAY_OWN_OPENGEX=ON`), choose **File > Import Model...** and pick `examples\own_readers\cube_spin.ogex` (shipped in the Windows release; typed or generated by us, `docs/provenance_audit.md` row 12d). The Console shows a warning line from our reader, `model import '...cube_spin.ogex': OpenGEX: texture coordinates are kept as written ...`; Assimp writes no such line, so with the variable unset (Assimp reads the file) it is missing. `tests/test_own_e4_samples.cpp` (`own_e4_samples`) imports the three sample files through the seam with the own backend and checks the result; `own_e4_default` checks `-DOKAY_OWN_OPENGEX=ON`. Not verified: a run on Windows, the editor's clip list for the imported model, any real-world file.

## What it is

OpenGEX (Open Game Engine Exchange) is a scene format by Eric Lengyel, written in OpenDDL, a small text data language. A file holds a node tree, geometry objects (meshes), materials, skins and animation tracks.

| File | What |
|---|---|

| `engine/src/Render/OgexReader.cpp` | `okay::ReadOgexBuffer` / `okay::ReadOgexFile` (declared in `ModelData.hpp`) |

## What it reads

**OpenDDL.** Structures `Name $global %local (property = value, ...) { ... }` and the primitive data structures (`bool`, `int8` to `int64`, `unsigned_int8` to `unsigned_int64` (also `uint8` ..., and the short names `u8`, `f`, `d` ...), `half`, `float`, `double`, `string`, `ref`, `type`, with an optional `[n]` and sub-arrays `{{...}, {...}}`); `//` and `/* */` comments; integer literals in decimal, `0x`, `0o`, `0b`, as `'c'` characters and with `_` separators; floats in decimal, and a hex, octal or binary literal as the IEEE bit pattern; strings with escapes and adjacent strings joined; references (`$a`, `%b`, `$a%b`, `null`). A sub-array must hold exactly `n` values (the grammar notes say so; a file that does not is refused).

**OpenGEX.** `Metric` (`distance` scales the root node, `angle` and `time` scale rotation angles and key times, `up` "z" turns the root by -90 degrees about X, as the other Z-up readers do). `Node`, `BoneNode`, `GeometryNode`, `CameraNode`, `LightNode` as nodes (camera and light nodes stay empty nodes) with `Name`, `Transform` (a 4x4 matrix, column-major as the specification says), `Translation`, `Rotation` (`x`, `y`, `z`, `axis`, `quaternion`) and `Scale` (`x`, `y`, `z`, `xyz`). Several transform structures on one node compose **in file order, first listed outermost** (`M = T1 * T2 * ...`, column vectors): this is my reading of the specification and is checked in the tests (Translation then Rotation gives a node at the translation; Rotation then Translation turns the translation), but not against a real file. A transform marked `object` is baked into that node's own geometry and leaves the node's children alone. `GeometryObject` with its first full-detail `Mesh`: primitive `triangles`, `quads` (two triangles each) or `triangle_strip` (with the `restart` index; alternate triangles have their first two vertices swapped), `VertexArray` `position`, `normal` and the first `texcoord`; one part per `IndexArray`, holding only the vertices that array uses, its `material` index taken through the node's `MaterialRef`s; `front = "cw"` reverses the winding; a mesh with no index array is read as its vertices in sequence. Smooth normals are made when the file has none. `Material`: `Color` `diffuse`, `emission` and `opacity`, `Param` `specular_power` (as shininess) and `opacity`, `Texture` `diffuse`, `normal` and `specular`. `Skin`: as I recall the specification it holds a `Transform` (the bind-shape matrix), a `Skeleton` structure with the `BoneRefArray` and a `Transform` of one bind matrix per bone, and then `BoneCountArray`, `BoneIndexArray`, `BoneWeightArray` (the four strongest weights of each vertex, normalised; a vertex with no weight is tied to the root). **Both layouts are accepted**: `BoneRefArray` inside `Skeleton` (preferred) or directly under the Skin. The bind pose of a bone is the matrix from `Skeleton/Transform` when it holds one matrix per bone (read as the bone-to-object bind transform), else the bone node's own world transform at load; `inverseBind = inverse(bind pose) * skinTransform`. **Unverified:** whether the specification's per-bone matrices are the bind pose or its inverse, and the whole layout, are from memory (not checked against a document or a real file); a real skinned file may still be refused or bound wrongly. A skinned part sits on the root node, like the other skinned readers. `Animation` / `Track` / `Time` / `Value` / `Key`: one clip per `clip` index (named by a `Clip` structure, else "animation" when it is the only one and "clipN" otherwise). A track names one transform structure of a node by its `%local` name (or `$node%local`). Each animated node gets one channel sampled at the **union of the key times of its tracks**: at each time every transform structure of the node is evaluated (animated ones by linear interpolation of their keys, quaternions by normalised lerp; the others at their file value), composed and decomposed to a position, rotation and scale key. Keys are sorted by time when they were not.

**Texture coordinates are kept as written**: my reading of the specification is that OpenGEX puts the origin at the upper left of the image (the engine's convention), so no flip is made. That is **unverified**; if real exporters write v upward, the readers of this family flip it.

## Not handled (each is a line in `out.notes`)

`CameraObject` and `LightObject` (the nodes stay empty), `Extension` structures, vertex `color`, `tangent`, `bitangent` and further texture coordinate sets, morph targets and `MorphWeight`, level-of-detail meshes (only the first is read), points, lines and line strips, bezier and TCB curve tangents (the `value` keys are joined by straight lines), material attributes other than the ones above, textures other than diffuse, normal and specular, texture transforms, an object-only transform on a skinned mesh, unknown top-level structures.

## Limits

File 128 MiB. Parser: 1,000,000 structures, nesting depth 256 (an explicit stack; no recursion), 16,000,000 numbers, 4,000,000 string or reference values, 64 MiB of string bytes, 64 properties on a structure, sub-array size 4096, a number between -1e15 and 1e15 (finite). Reader: 200,000 nodes, 100,000 materials, 2,000,000 vertices and 4,000,000 triangles over all meshes (each mesh is built once), 6,000,000 vertices and 4,000,000 triangles placed in the scene (a mesh used by many nodes counts once per node), 4,096 bones per skin and 1,000,000 bone entries copied into parts over the file (bones x placements; the bone list is built once per mesh), 4,000,000 animation keys, 256 transform structures per node, 20,000,000 animation samples x transforms, 4,096 clips, 1,000,000 tracks. Every count is checked before the memory is taken, and an overrun gives a message that names the budget. Text with a UTF-8 or UTF-16 byte order mark is converted. **Texture paths** go through `SceneRefPath.hpp::ResolveInsideDir`: an absolute path, a drive letter, a `..` that climbs out of the model's folder and a path through a link that leaves it are refused (the model still reads; the material has no texture and a note names the first refused path).

## Tests and what was checked

- `ogex_reader` (305 checks): the grammar (every literal form, properties, names, comments, escapes) and 22 grammar errors, each refused with a line number; the parser budgets; a quad with a material, a Z-up scene and a distance metric (positions, node tree, scale and rotation of the root, material, texture path); UTF-8 and UTF-16 with a byte order mark; refused texture paths; quads, strips, restart, `cw`, no index array, two index arrays with materials, line meshes, an out-of-range index; matrix, transform order, quaternion, axis, one-axis scale, object-only transform, angle metric, node names; a two-bone skin (weights 0.25 / 0.75, inverse binds, the skin transform), bone counts that do not add up, a count of 4,294,967,295, a missing bone; a two-clip animation (key times, interpolated values, quaternion values at 0.5 and 1.0 radians), the time metric, a missing target, unequal key counts, keys out of order, negative times; every 7th truncation of the quad file.
- `e4_hostile`: 1,000,000 open structures (refused at depth 256 in under a millisecond), 1,100,000 structures, 250,000 nested nodes, 200,001 sibling nodes, 16,000,001 numbers, 12.3 million indices, 2.1 million vertices, one mesh of 100,000 triangles named by 50 nodes (refused) and by 30 (read), a skin with bone counts of 4,294,967,295, 4,100 clips, 4,100,001 keys, coordinates of 1e15, a 3 MB texture path; each case under 8 s and under 640 MB (a counting `operator new` measures the peak; the largest peak was 222 MB); then 4,000 mutations of each of three seed files (40,000 in the sanitizer run).
- **Mutation checks** (a deliberate bug put into a copy of the reader, the test must fail): transform order reversed (2 checks fail), strip parity (3), bind shape left out of the inverse bind (1), distance metric ignored (1), parser depth limit raised (1). All were caught.
- After an outside review: the bone list is built once per mesh; the vertex remap table is shared; names are made unique by a loop; transform structures are indexed by local name (256 per node); integer-valued numbers are range-checked before every cast; new `e4_hostile` cases (a skinned mesh of 4,096 bones used by 50,000 nodes, a 500,000-vertex mesh used by 100,000 nodes, 20,000 transforms with 20,000 tracks, 300,000 keys x 256 transforms) and unit tests (Skeleton layouts, name collisions, 2^64 and 1e19 values) fail or hang on the code before the fix.
- Sanitizers: the whole of `e4_hostile` is clean under ASan, UBSan and float-cast-overflow with 40,000 mutations per seed.

## Provenance (what this file was written from)

`OpenDdl.hpp` and `OgexReader.cpp` were written from scratch for this project. **No document was consulted while writing them**: the OpenDDL grammar and the OpenGEX structures, properties and conventions (right-handed, column-major matrices, `Metric` keys, the index and skin array layouts) are **recalled from memory** of the public specification and are unverified against the text and against real files. **No code, comment, table or test from Assimp or any other importer was read, copied or ported, and no snippet from the web was used.** The test files are hand-written from the same recollection, so they test the reader against that recollection only.
